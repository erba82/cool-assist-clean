# قرارداد بازسازی موتورهای مهندسی Cool-Assist

این قرارداد با هدف جلوگیری از خروجی ظاهراً قطعی اما فاقد مبنای سازنده، جلوگیری از تبدیل ظرفیت ذخیره‌سازی به بار برودتی، و حفظ یک منبع حقیقت مشترک میان محاسبات، انتخاب، P&ID، BIM، BOM و Calculation Book تعریف شده است.

## 1. رفتار مکالمه و Design Basis

برنامه پس از استخراج درخواست، ابتدا یک **Design Basis پیشنهادی** ایجاد می‌کند. هر مقدار باید `source` داشته باشد: `user-declared`، `regional-dataset`، `manufacturer-document`، `calculated` یا `assumption-proposed`. هیچ مقدار با `assumption-proposed` به محاسبه یا selection نهایی وارد نمی‌شود، مگر کاربر آن را تأیید یا تغییر دهد.

| گروه ورودی | داده‌های لازم برای محاسبهٔ بار | رفتار در نبود داده |
|---|---|---|
| پروژه | location، refrigerant و کاربری | location/refrigerant از متن استخراج می‌شوند؛ مبرد فقط recommendation است تا تأیید user. |
| اتاق | طول، عرض، ارتفاع، setpoint، product/process | بدون این‌ها transmission/infiltration/internal load محاسبه نمی‌شود. |
| محصول | product، incoming temperature، pull-down زمان‌دار یا production rate | ظرفیت ذخیره‌سازی بر حسب tonne جایگزین product load نیست. |
| envelope | insulation construction یا U-value، floor condition، door traffic | برنامه مقدار پیشنهادی را جدا نمایش می‌دهد و تأیید می‌گیرد. |
| شرایط طراحی | evaporating/condensing temperature یا ambient/design approach | اگر نبود، regional-data یا assumption با فیلد منبع و confirmation لازم دارد. |
| انتخاب تجهیز | redundancy policy، compressor control philosophy و performance map | بدون curve/model revision، candidate تولید می‌شود اما final selection ممنوع است. |

> **قاعدهٔ مهم:** «خودت حساب کن» باید به پیشنهاد assumptions قابل‌ویرایش منجر شود، نه به تخمین پنهان. پس از تأیید، engine تمام component loadها را اجرا و یک schedule قابل‌ردیابی ایجاد می‌کند.

## 2. قرارداد انتخاب تجهیزات

هر ردیف selection باید شکل زیر را داشته باشد:

```json
{
  "category": "compressor",
  "selectionStatus": "candidate | manufacturer-map-required | verified-candidate | rejected",
  "manufacturer": "Mayekawa",
  "model": "250 VLD",
  "manufacturerModelKey": "MAYEKAWA_V_250_VLD",
  "operatingPoint": { "refrigerant": "R717", "evapC": null, "condC": null, "speedRpm": null },
  "performance": {
    "refrigerationCapacityKw": null,
    "absorbedPowerKw": null,
    "motorRatedKw": null,
    "cop": null,
    "mapRevision": null,
    "mapSource": null
  },
  "train": { "dutyCount": null, "standbyCount": null, "controlStrategy": null },
  "evidence": { "catalogueSource": [], "mapStatus": "required" },
  "blockingReasons": []
}
```

`manufacturer` و `model` از **یک record catalogue** می‌آیند و هرگز با tier یا brand تدارکاتی جایگزین نمی‌شوند. Tier فقط می‌تواند پیشنهاد procurement compatible تولید کند؛ در صورت نبود evidence سازگار، status باید `incompatible-with-engineering-selection` باشد. Model، capacity، motor rating، COP یا price فاقد curve، revision و operating point، باید `—` یا `manufacturer-map-required` باقی بماند.

### منطق تعدد کمپرسور

تعداد کمپرسور تنها زمانی عددی و قابل‌نمایش است که ظرفیت هر candidate در point مورد نظر از map معتبر خوانده شود. سپس engine بار design × safety/diversity policy را با مجموع duty capacity در worst selected state می‌سنجد و N+1 را به‌صورت `dutyCount + standbyCount` گزارش می‌کند. بدون این داده‌ها، برنامه می‌تواند topology پیشنهادی مثل **multi-compressor screw train, redundancy policy approval required** ارائه کند، ولی حق نمایش «2+1، 1150 kW، 600 kW» ندارد.

## 3. قرارداد چرخه، P&ID و BIM برای R717 pumped recirculation

P&ID باید یک graph process باشد، نه layout preview. هر node باید `componentRole`، `manufacturerModelKey` یا `manufacturer-map-required`، `tag`، `sourceEvidence` و port status داشته باشد. هر line باید `fromPort`، `toPort`، `flowDirection`، `service`، `design pressure`، `DN status`، `joint policy` و `line-list id` داشته باشد.

چرخهٔ پیشنهادی R717 pumped recirculation باید نقش‌های زیر را به‌صورت مجزا و traceable داشته باشد: compressor train، oil separation/cooling، heat rejection، HP receiver، controlled HP-to-LP feed، LP pump separator/surge drum، pump(s)، pumped liquid header، valve station، evaporator(s) و wet-return header. نبود هر نقش باید reason داشته باشد؛ node عمومی با عنوان `horizontal vessel` جایگزین نقش process نیست.

## 4. قرارداد elevation و NPSH

Renderer اجازه ندارد از position نمایشی P&ID، elevation ساختگی تولید کند. elevation تنها از `plantLayout.elevationDatumM` و `plantLayout.equipment[tag]` مصرف می‌شود؛ UI باید وضعیت آن را به‌روشنی نمایش دهد.

| رابطه | شرط قابل‌اعتبارسنجی | وضعیت بدون داده |
|---|---|---|
| LP separator ↔ compressor suction | elevation واقعی nozzle centerline separator و suction compressor لازم است؛ separator باید بالاتر بودن رابطهٔ gravity/suction را نشان دهد. | `layout-input-required` |
| LP separator ↔ pump suction | elevation nozzle، pump suction centerline، NPSHr map و pressure-loss suction line لازم‌اند؛ NPSHa باید محاسبه و با margin بررسی شود. | `npsh-input-required` |
| thermosiphon source ↔ oil cooler | liquid level thermosiphon source، oil-cooler centerline، flow/overfeed و pressure-loss loop لازم‌اند؛ head باید محاسبه شود. | `thermosiphon-head-input-required` |
| condenser ↔ thermosiphon ↔ HP receiver | nozzle elevations، flow-through/elevated-system configuration و hydraulic data لازم‌اند؛ graph باید path را اثبات کند. | `topology-or-layout-input-required` |

راهنمای Frick حداقل head متعارف بیش از ۱٫۸ m را توضیح می‌دهد، اما تصریح می‌کند که مقدار واقعی تابع pressure drop و design است؛ این مقدار هرگز به‌عنوان set-out قطعی یا NPSH margin ثابت در نرم‌افزار کدگذاری نمی‌شود. [1]

## 5. Calculation Book و چاپ

Calculation Book دارای دو presentation جدا است: صفحهٔ interactive و `print-report`. print-report باید Landscape/A4، revision/date، designer review disclaimer، design basis، assumptions register، load schedule، thermodynamic provider status، pipe sizing status، equipment selection evidence، BOM status و limitations register داشته باشد. `window.print()` نباید shell/chat/sidebar/canvas برنامه را چاپ کند.

## 6. Acceptance tests

1. هیچ record انتخاب‌شده نباید model و manufacturer ناسازگار داشته باشد.
2. با storage capacity بدون declared load، total load و estimate load نباید عدد ظاهر کند.
3. با declared load، component-load schedule و source هر assumption ظاهر شود.
4. با map missing، compressor candidate باید capacity/motor/COP/price را قطعی نشان ندهد و final issue blocked بماند.
5. P&ID باید برای cycle R717 نقش‌های process و direction قابل‌خواندن داشته باشد و هر DN نامشخص در line-list به status review منتقل شود، نه label مبهم تکرارشونده.
6. BIM با elevation data غایب باید layout-input-required نشان دهد؛ با data کامل، relation checks و NPSH/thermosiphon checks اجرا شوند.
7. Print report فقط report shell را چاپ کند.
