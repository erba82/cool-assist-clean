# وضعیت و برنامهٔ پیاده‌سازی Provider معتبر خواص ترمودینامیکی

**تاریخ:** ۲۱ اوت ۲۰۲۶
**اصل طراحی:** افزودن adapter قابل‌ردیابی و review-gated، بدون حذف مسیرهای موجود و بدون اتصال خودکار به سرویس بیرونی.

## ۱. وضعیت واقعی فعلی

| حوزه | وضعیت مشاهده‌شده | نتیجهٔ مهندسی |
|---|---|---|
| Connector در نشست | هیچ connector سفارشی یا connector با نام property/provider وجود ندارد | provider بیرونی فعال نیست و هیچ credential یا مجوزی در اختیار برنامه نیست |
| API capability | R717 برابر `internal-table-review-required` است؛ هفت مبرد دیگر `validated-property-provider-required` هستند | برنامه به‌درستی انتخاب نهایی را برای خواص معتبر باز می‌گذارد |
| جدول داخلی | فقط R717 جدول اشباع داخلی دارد؛ source revision، uncertainty، reference state، license و envelope ثبت نشده است | جدول فقط دادهٔ مقدماتی/بازبینی‌شونده است، نه منبع validated |
| ThermodynamicCycleAnalyzer | از interpolation جدول R717 و تقریب‌های ثابت برای superheat، discharge temperature، subcool و entropy استفاده می‌کند | خروجی فعلی cycle preliminary است و نباید به‌عنوان cycle/property validated معرفی شود |
| RefrigerantProps | برای چند مبرد همبستگی ساده دارد و در نام ناشناخته به R404A default می‌شود | این مسیر باید در چرخهٔ بعدی به compatibility-only / review-required محدود شود؛ نباید provider نهایی تلقی شود |
| Performance map سازنده | در capability صریحاً `manufacturer-performance-map-required` است | انتخاب کمپرسور و performance نهایی بدون نقشهٔ سازنده تأییدشده کامل نیست |

## ۲. گزینهٔ provider و تصمیم معماری

| گزینه | کاربرد مناسب | وضعیت مجوز/استقرار | تصمیم |
|---|---|---|---|
| CoolProp | prototype/review adapter برای خواص pure/pseudo-pure/mixture؛ امکان query state با دو ورودی مستقل | open-source و قابل استقرار محلی؛ version/backend/reference state باید ثبت شود | کاندید مرحلهٔ اول برای adapter محلی، فقط پس از تست محدوده و تأیید مهندس |
| NIST REFPROP 10 | مسیر high-assurance برای پروژه‌های نیازمند دیتای مرجع و mixtureهای پیچیده | نرم‌افزار/مجوز تجاری؛ site/distributor licence و runtime کنترل‌شده لازم است | backend اختیاریِ ارجح در صورت تأمین مجوز و مسیر runtime توسط مالک |
| جدول داخلی R717 | حفظ سازگاری نمایش و preliminary checks | source metadata ناقص | فقط fallback با warning؛ هرگز جای provider validated را نمی‌گیرد |

CoolProp خود گزارش می‌کند که `PropsSI` با دو متغیر مستقل وضعیت را تعیین می‌کند و برای اشباع باید T یا P همراه با Q اعمال شود. اعمال دستی phase فقط وقتی مجاز است که phase فیزیکی قطعاً معلوم باشد. REFPROP 10 از سوی NIST به‌عنوان مدل‌های critically evaluated برای سیالات و مخلوط‌ها معرفی شده و library قابل فراخوانی دارد، ولی یک محصول مجوزدار است. [1] [2]

## ۳. قرارداد canonical adapter

تمام adapterها باید یک قرارداد SI-only را پیاده کنند. UI می‌تواند واحدهای دیگر نمایش دهد، اما هیچ تبدیل واحدی نباید داخل providerهای متفاوت پنهان شود.

```js
// درخواست canonical
{
  refrigerant: 'R717',
  backend: 'coolprop-heos' | 'refprop',
  state: { input1: { key: 'T', valueSI: 243.15 }, input2: { key: 'Q', valueSI: 1 } },
  outputs: ['P', 'Dmass', 'Hmass', 'Smass', 'Cpmass', 'VISCOSITY'],
  referenceState: 'IIR',
  purpose: 'cycle-preliminary' | 'hydraulic-review' | 'selection-review'
}

// پاسخ canonical
{
  status: 'ok' | 'review-required' | 'out-of-range' | 'provider-unavailable',
  valuesSI: { P: 119500, Dmass: 1.02, Hmass: 1416000, Smass: 5460 },
  provenance: {
    providerId: 'coolprop' | 'refprop',
    providerVersion: 'required',
    backend: 'HEOS' | 'REFPROP',
    fluidIdentifier: 'NH3',
    referenceState: 'IIR',
    sourceRevision: 'required',
    queriedAt: 'ISO-8601',
    inputsSI: [],
    applicability: { status: 'validated-by-provider' | 'review-required', note: '' }
  },
  reviewRequired: true | false,
  warnings: []
}
```

## ۴. گیت‌های اجباری

1. مبرد باید در profile و allow-list provider ثبت شده باشد؛ fallback به مبرد دیگر ممنوع است.
2. هر مقدار ورودی و خروجی باید finite، SI و دارای unit contract باشد.
3. هر state باید دو متغیر مستقل یا ترکیب مجاز T/P/Q/H/S داشته باشد؛ T/Q و P/Q فقط در محدودهٔ اشباع مجازند.
4. phase imposed باید به‌صورت پیش‌فرض ممنوع باشد مگر اینکه caller دلیل و status آن را ثبت کند.
5. reference state، provider version، fluid mapping، source revision و timestamp باید در provenance بازگردند.
6. provider unavailable یا out-of-range باید status قابل‌نمایش برگرداند، نه عدد پیش‌فرض.
7. cycle/preliminary و selection/final باید دو purpose مجزا داشته باشند؛ final selection علاوه بر provider به map سازنده و review نیاز دارد.
8. REFPROP تنها با license/runtime owner-approved فعال می‌شود. هیچ DLL یا credential در Git یا runtime عمومی قرار نمی‌گیرد.
9. اتصال HTTP/MCP به provider هرگز خودکار فعال نمی‌شود؛ allow-list، timeout، admin approval و test vector لازم است.

## ۵. برنامهٔ پیاده‌سازی مرحله‌ای

| مرحله | کار | معیار پذیرش | تغییر روی قابلیت موجود |
|---|---|---|---|
| A. foundation | registry محلی provider، allow-list مبرد، env-driven status و health contract | provider در حالت پیش‌فرض `not-configured` است؛ هیچ request شبکه‌ای نمی‌رود | هیچ مسیر فعلی حذف نمی‌شود |
| B. adapter contract | interface canonical، validation ورودی/خروجی، provenance و error taxonomy | testهای nominal، invalid، non-finite، out-of-range و unavailable عبور کنند | analyzer قدیمی همچنان compatible باقی می‌ماند |
| C. CoolProp sidecar | سرویس محلی/approved endpoint با version pin و vector tests | مقایسهٔ بردارهای مرجع توسط مهندس؛ ثبت version/backend/reference state | فعال‌سازی فقط با env و approval |
| D. cycle integration | ThermodynamicCycleAnalyzer ابتدا adapter را می‌پرسد؛ در نبود آن preliminary status را حفظ می‌کند | هیچ result validated بدون provenance تولید نشود | خروجی legacy حذف نمی‌شود؛ provenance افزوده می‌شود |
| E. REFPROP optional | adapter مجوزدار با health check، licence gate و data locality | license/host approved، independent validation و audit trail | فقط provider جدید اضافه می‌شود |
| F. manufacturer maps | performance map و operating envelope سازنده به selection وصل شود | انتخاب نهایی تنها با map/source معتبر | semantic selection فعلی حفظ می‌شود |

## ۶. اقدام شروع‌شده در این iteration

در این iteration فقط foundation و contract آغاز می‌شود: registry وضعیت provider، allow-list، policy، endpoint read-only و testهای بدون اتصال بیرونی. نصب CoolProp، اجرای sidecar، اتصال HTTP، افزودن credential یا فعال‌سازی REFPROP در این مرحله انجام نمی‌شود؛ همهٔ آن‌ها نیازمند تصمیم مالک دربارهٔ محیط استقرار، مجوز و منبع تأییدشده‌اند.
