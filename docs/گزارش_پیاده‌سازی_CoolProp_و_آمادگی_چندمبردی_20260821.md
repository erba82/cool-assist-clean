# گزارش پیاده‌سازی CoolProp Local Sidecar و آمادگی چندمبردی

**تاریخ:** ۲۱ اوت ۲۰۲۶
**وضعیت:** پیاده‌سازی افزایشی، قابل‌بازگشت و review-gated؛ هیچ قابلیت موجود حذف نشده است.

## نتیجهٔ صریح

پیش از این مرحله، برنامه برای هر هشت مبرد دارای پروفایل، template معنایی چرخه و P&ID بود؛ اما یک provider معتبر خواص برای هفت مبرد نداشت، مسیر legacy `DesignGenerator` به‌صورت نادرست چرخهٔ آمونیاک را فراخوانی می‌کرد و کاتالوگ برای اغلب مبردها evidence سازندهٔ قابل‌انتخاب نداشت. بنابراین پاسخ دقیق به سؤال «آیا همه‌چیز برای همه مبردها آماده بود؟» **خیر، به‌طور کامل آماده نبود**.

در این مرحله، خواص provider-based برای هر هشت مبرد، چرخهٔ مقدماتی DX/فشرده‌سازی بخار برای هفت مبرد، و مدل مقدماتی مستقل R744 transcritical-booster اضافه شد. P&ID و BIM semantic قبلی حفظ شده‌اند، اما انتخاب نهایی تجهیز و BIM manufacturer-specific فقط در صورت وجود declaration صریح سازنده و source reference اجازهٔ candidate شدن دارد.

| لایه | وضعیت پس از این مرحله | گیت باقی‌مانده |
|---|---|---|
| پروفایل و چرخهٔ معنایی | ۸ مبرد: R717، R744، R290، R32، R404A، R410A، R134a و R22 | بازبینی پروژه/ایمنی |
| P&ID | template اختصاصی تمام ۸ مبرد؛ برای R744 شامل gas cooler، HPV، FGR و EEV | بازبینی topology و sizing پروژه |
| خواص | CoolProp 8.0.0/HEOS، SI-only، provenance و reference state IIR، sidecar loopback | environment، validity envelope و review مهندس |
| چرخهٔ ساده | R717، R290، R32، R404A، R410A، R134a و R22 با sidecar | map سازنده و envelope تجهیز |
| چرخهٔ R744 | booster transcritical مقدماتی با high-side و flash-gas صریح | optimization کنترل، ejector/parallel compression، heat reclaim و map سازنده |
| تجهیزات | readiness matrix و منع substitution بین مبردها | دادهٔ معتبر سازنده برای اغلب category/refrigerantها |
| BIM | semantic equipment role و pipe policy بر پایهٔ مبرد حفظ شده است | mapping مدل‌های manufacturer-backed و GA/port evidence |

## sidecar محلی CoolProp

sidecar در `backend/thermophysical-sidecar/` پیاده‌سازی شد. این سرویس فقط روی `127.0.0.1:5011` bind می‌شود، outbound internet request ندارد، محیط Python مجزا در `.venv` می‌سازد و `CoolProp==8.0.0` را با pin نسخه اجرا می‌کند. API فقط SI می‌پذیرد و هر پاسخ شامل version، revision، backend، fluid identifier، reference state، inputها و timestamp است. هر مقدار حاصل‌شده `reviewRequired: true` باقی می‌ماند.

| کنترل | رفتار |
|---|---|
| ورودی properties | دقیقاً دو ورودی مستقل از T[K]، P[Pa]، Q، Hmass[J/kg]، Smass[J/kg/K] یا Dmass[kg/m³] |
| خروجی | فقط allow-list خواص SI و نتیجهٔ finite |
| فعال‌سازی | `THERMOPHYSICAL_PROVIDER_MODE=coolprop-sidecar`، URL loopback و flag صریح لازم است |
| خطا | input نامعتبر، fluid ناشناخته، state حل‌نشده و نتیجهٔ non-finite بدون fallback ساختگی گزارش می‌شود |
| policy | URL غیرمحلی در Node adapter رد می‌شود؛ registry و backend به‌طور پیش‌فرض provider را خاموش نگه می‌دارند |

CoolProp برای Python 3.12+ wheel پایدار ABI ارائه می‌کند و مستندات آن `PropsSI` با واحدهای پایهٔ SI را بیان می‌کند. مجوز CoolProp MIT است؛ این مجوز به‌تنهایی اعتبار طراحی یا انتخاب تجهیز ایجاد نمی‌کند. [1] [2]

## مدل R744 transcritical-booster

R744 عمداً در endpoint چرخهٔ ساده مسدود است. endpoint جداگانهٔ `/v1/cycle/r744-transcritical-booster` ورودی‌های `evapTempK`، `gasCoolerOutletTempK`، `highSidePressurePa`، `flashGasPressurePa`، دو راندمان ایزنتروپیک و `loadW` را می‌گیرد. pressure ordering، عبور high-side از critical pressure، split فلش‌گس، positive refrigerating effect و توان finite کنترل می‌شوند.

آزمون زنده با بار 100 kW، `T_evap=-30°C`، `T_gas-cooler-out=35°C`، فشار high-side برابر 9 MPa و فشار flash برابر 3.6 MPa اجرا شد. پاسخ CoolProp 8.0.0 finite بود، COP مقدماتی 1.4911 تولید کرد و `reviewRequired=true` ماند. این عدد **بهینه‌سازی کنترل یا انتخاب کمپرسور نیست**؛ صرفاً اثبات عملکرد قرارداد نرم‌افزاری است.

## مقایسه با legacy و اصلاح مسیر چندمبردی

مقایسهٔ موازی R717 در شرایط سناریوی دبی نشان داد فشارهای اشباع legacy با CoolProp نزدیک‌اند، اما COP legacy حدود 74.37 درصد با خروجی provider اختلاف دارد و توان کمپرسور اختلاف بزرگ‌تری نشان می‌دهد. این نتیجه نشان می‌دهد legacy برای selection-ready مناسب نیست و نباید با عنوان «دقیق» عرضه شود. adapter جدید آن را جایگزین یک‌باره نکرده است؛ نتیجهٔ sidecar فقط با provenance و review gate در دسترس است و مسیر legacy برای compatibility حفظ شده است.

`DesignGenerator` نیز اصلاح شد تا مبرد کاربر را normalize کند، برای R290/R32/R404A/R410A/R134a/R22 از چرخهٔ sidecar همان مبرد استفاده کند و هرگز آمونیاک را به‌جای مبرد دیگر substitute نکند. در نبود sidecar، status شفاف `validated-property-provider-required` می‌دهد. برای R744، نبود pressure controls با `r744-operating-controls-required` گزارش می‌شود؛ setpoint اختراع نمی‌شود.

## تجهیزات، لوله‌کشی، P&ID و BIM

مولد اجزای legacy پیشتر مدل‌های ساختگی مانند `N320VLD-*`، `OPTIGO-Plus` و `DANFOSS-TEN` و همچنین نام‌ها و sizing عمومی مستقل از مبرد تولید می‌کرد. این مسیر اکنون از `RefrigerantProfiles` و `CatalogueRepository` استفاده می‌کند. اجزا role معنایی مبرد، policy متریال و joint، cycle و feed method را دریافت می‌کنند. مدل فقط در صورت سازگاری صریح کاتالوگ با مبرد انتخاب‌شده برگردانده می‌شود؛ در غیر این صورت `null` و status review-required ثبت می‌شود.

ماتریس readiness جدید نشان داد فقط R717 و R22 در dataset فعلی دست‌کم یک category دارای source-backed compressor record دارند. برای R744، R290، R32، R404A، R410A و R134a هنوز manufacturer-compatible catalogue evidence در dataset فعلی وجود ندارد. برنامه اکنون این کمبود را آشکار می‌کند و اجازهٔ جایگزینی یک compressor R717 در طراحی DX یا CO₂ را نمی‌دهد. این محدودیت داده است، نه نقصی که مجاز باشد با مدل ساختگی پنهان شود.

## محدودیت‌ها و برنامهٔ ادامه

گام بعدی صحیح، جمع‌آوری manufacturer performance maps و کاتالوگ سازگار برای هر category/refrigerant است؛ سپس map interpolation با envelope و revision در selection engine اضافه می‌شود. برای R744، بهینه‌سازی high-side pressure، heat reclaim، ejector یا parallel compression فقط پس از تعریف کنترل‌های پروژه و evidence سازنده انجام می‌شود. برای R717، اختلاف بزرگ legacy/provider باید با test vectors تأییدشده توسط مهندس بررسی و سپس legacy calculator به‌صورت کنترل‌شده deprecate شود. هیچ‌یک از این موارد نباید با مقدار پیش‌فرض یا قیمت/مدل ساختگی جایگزین شود.
