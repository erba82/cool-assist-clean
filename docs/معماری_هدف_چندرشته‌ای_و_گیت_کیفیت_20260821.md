# معماری هدف چندرشته‌ای و گیت کیفیت Cool-Assist

این سند، اولین اجرای مانیفست فنی است. هدف آن افزودن HVAC و Electrical بدون انشعاب دادن منطق تبرید یا coupling میان UI، AI، محاسبات و renderer است. در این مرحله هیچ engine جدید HVAC/Electrical به‌عنوان محاسبهٔ واقعی معرفی نمی‌شود؛ فقط قراردادها، registry قابلیت و گیت‌های مشترک ایجاد می‌شوند.

## مرزهای معماری

تبرید فعلی به‌عنوان تنها discipline عملیاتی حفظ می‌شود. HVAC و Electrical فقط با وضعیت `planned` اعلام می‌شوند و هر درخواست design آن‌ها باید به‌طور شفاف blocker و requirements لازم را بازگرداند. از آنجا که سیستم هنوز intent classifier و parser مشترک دارد، افزودن registry نباید تغییر رفتار `DesignOrchestrator` یا مسیر تبرید ایجاد کند.

| لایه | مسئولیت | عدم مسئولیت |
|---|---|---|
| Intent | تعیین discipline، scope، location، evidence و inputs مفقود | انتخاب تجهیز یا مقدار محاسباتی |
| Discipline engine | physics، selection، safety و graph discipline خود | render و state رابط کاربر |
| Evidence | source/revision/license/state و provenance | تبدیل خودکار evidence ناقص به نتیجهٔ قطعی |
| Design graph | nodes، ports، connections، services و relationshipهای قابل‌ردیابی | ذخیرهٔ مستقیم mesh یا UI state |
| Review gate | جمع‌بندی blockers و اجازه/عدم اجازهٔ مرحلهٔ بعد | تغییر قانون یا approval خودکار |
| Delivery | report، BOM، P&ID/BIM/export با revision | صدور تلقایی IFC/construction issue |

## EngineeringSystemContract v1

```js
{
  projectId: 'string',
  discipline: 'refrigeration | hvac | electrical',
  systemType: 'string',
  operatingConditionsSI: {},
  intent: { source: 'user | document | ai-extraction', confidence: 0, missingInputs: [] },
  evidence: [{ id, type, source, revision, effectiveDate, licenseState, status }],
  graph: { nodes: [], connections: [], revision: 'string' },
  calculation: { provider, status, results: {}, assumptions: [] },
  selection: { status, candidates: [], blockers: [] },
  review: { status, gates: [], blockers: [], finalIssueAllowed: false }
}
```

تمام اعداد SI در engine و evidence نگه‌داری می‌شوند. UI می‌تواند واحد را تبدیل کند، اما نام unit و conversion source باید قابل‌ردیابی باشد. فیلدهای اختیاری `calculation` و `selection` هرگز نباید با `0` یا string ساختگی پر شوند تا ظاهر کامل‌تری ایجاد کنند.

## DisciplineCapabilityRegistry

registry باید تنها source برای اعلام readiness باشد. `refrigeration` با جزئیات قابلیت موجود نشان داده می‌شود؛ `hvac` و `electrical` با capability contract و blockers به‌عنوان planned قابل‌رؤیت‌اند. این design مانع از آن می‌شود که frontend یا chat، رشته‌ای را قبل از engine و evidence واقعی «supported» معرفی کند.

| Discipline | وضعیت اکنون | اولین engine واقعی لازم | نخستین evidence gate |
|---|---|---|---|
| Refrigeration | governed beta | CoolProp/provider + manufacturer performance map | refrigerant compatibility، operating envelope و source revision |
| HVAC | planned | psychrometric/provider، heat-load و duct/air-side solver | weather/design condition، space data و AHU/terminal data |
| Electrical | planned | demand/load، voltage-drop، short-circuit و protection coordination | utility data، equipment nameplate و protection curve |

## ReviewGatePolicy

گیت‌ها `input`، `physics`، `graph`، `selection` و `delivery` هستند. هر گیت وضعیت `passed`، `review-required` یا `blocked` دارد. اگر input missing، calculation preliminary، equipment evidence missing، graph ports unresolved یا delivery document incomplete باشد، `finalIssueAllowed=false` خواهد بود. این ارزیابی یک service pure و read-only است و در گام اول خروجی فعلی را مسدود نمی‌کند؛ بلکه readiness قابل‌مصرف برای UI، report و future export فراهم می‌کند.

## APIهای نخستین

| Route | اثر | هدف |
|---|---|---|
| `GET /api/core/disciplines` | read-only | نمایش capability matrix صادقانه |
| `GET /api/core/disciplines/:code` | read-only | معرفی requirements و blockers هر discipline |
| `POST /api/core/review-gates/evaluate` | read-only | ارزیابی payload canonical بدون mutation یا اتصال بیرونی |

## معیار پذیرش پیاده‌سازی اول

۱. تمام سه discipline در registry وجود دارند اما فقط تبرید operational است.

۲. registry نباید یک مورد HVAC/Electrical را `production-ready` اعلام کند.

۳. review gate باید payloadهای missing evidence، preliminary calculation، unresolved port و incomplete delivery را به‌صورت deterministic و finite تشخیص دهد.

۴. هیچ route یا UI فعلی تبرید تغییر behavior ندهد؛ regression فعلی سبز بماند.

۵. testهای nominal، invalid discipline و final issue prohibition به suite backend اضافه شوند.
