# گزارش اجرای P0 تا P4: حاکمیت پایلوت تبرید صنعتی

**تاریخ:** 2026-08-21
**دامنه:** تبرید صنعتی، با تمرکز بر مسیر پایلوت review-gated برای R717 و R744
**وضعیت سند:** گزارش اجرای فنی؛ این سند مجوز ساخت، خرید، ایمنی، انطباق مقرراتی یا انتشار نهایی مهندسی نیست.

> تمامی خروجی‌های جدید عمداً در وضعیت **review-required** نگه داشته شده‌اند. هیچ مسیر جدیدی اجازهٔ انتخاب نهایی تجهیز، سفارش خرید یا construction issue را صادر نمی‌کند.

## 1. نتیجهٔ اجرایی

این مرحله چهار gap اصلی backlog پایلوت را به یک زنجیرهٔ قابل‌ردیابی متصل می‌کند: سلامت runtime خواص ترمودینامیکی، قرارداد evidence سازنده، golden case کنترل‌شده و scorecard اندازه‌گیری‌شده. طراحی به گونه‌ای انجام شده است که نبود provider، نبود revision یا envelope سازنده، نبود امضای انسانی روی golden case و variance بدون root cause همگی مسیر پیشرفت را **fail-closed** مسدود کنند.

| backlog | خروجی پیاده‌سازی‌شده | وضعیت عملیاتی |
|---|---|---|
| PILOT-001 | `SidecarHealthGovernor`، endpoint runtime status، runbook restart دستی | فعال و healthy در loopback؛ final selection همچنان false |
| PILOT-003 | `ManufacturerEvidenceContract` و اتصال به `CatalogueRepository` | فعال؛ record کاتالوگ بدون evidence کامل به `manufacturer-evidence-required` تنزل می‌یابد |
| PILOT-002 | `GoldenCaseRegistry` و taxonomy variance | فعال؛ fixture فقط از golden case امضاشده ساخته می‌شود |
| PILOT-004 | `PilotScorecard` و `PilotReadinessEvaluator` برای G0 تا G4 | فعال؛ KPIها فقط از رخدادها و evidence واردشده محاسبه می‌شوند |

## 2. حاکمیت runtime خواص ترمودینامیکی

`backend/core/engineering/SidecarHealthGovernor.js` به صورت تناوبی سلامت sidecar محلی را رصد می‌کند. Endpoint زیر یک observation تازه از `127.0.0.1:5011` می‌گیرد و علاوه بر version، git revision، backend، reference state و تعداد fluid mapping، گیت انتخاب را بازمی‌گرداند.

```text
GET /api/core/thermophysical-provider/runtime-status
```

| حالت health | اجازهٔ کار روی candidate مبتنی بر property | اجازهٔ final selection |
|---|---:|---:|
| `healthy` و fresh | فقط review-gated | خیر |
| `unavailable` | خیر | خیر |
| `stale` | خیر | خیر |
| `not-checked` | خیر | خیر |

سرویس backend **هرگز** sidecar را خودکار restart نمی‌کند. launcher در `backend/thermophysical-sidecar/start-sidecar.ps1` نیز اجرای process دوم روی همان پورت را رد می‌کند. در رخداد failure، اپراتور باید diagnostics را حفظ کند، sidecar را دستی با launcher اجرا کند، `/health` را کنترل کند، suite یکپارچه را دوباره اجرا کند و version/revision را وارد ledger بازبینی نماید.

## 3. قرارداد evidence سازنده و کاتالوگ

`ManufacturerEvidenceContract` برای رسیدن به `verified-candidate` الزام‌های زیر را اعمال می‌کند. این‌ها **حداقل metadata** هستند؛ حتی عبور از این validator انتخاب نهایی را مجاز نمی‌کند.

| گروه evidence | شرط اجباری |
|---|---|
| هویت record | `evidenceId`، category، manufacturer و model |
| منبع | `source`، `revision` و license state معتبر |
| سازگاری مبرد | refrigerant declaration صریح و تطابق با مبرد انتخاب‌شده |
| performance | reference و reference conditions در SI |
| envelope | operating envelope در SI |
| اتصال | حداقل یک port با id، نوع اتصال و DN/قطر اسمی finite |
| زمان اعتبار | expiry date در صورت وجود؛ در غیر این صورت warning برای review انسانی |

`CatalogueRepository.resolve()` دیگر source reference موجود را معادل انتخاب تأییدشده نمی‌داند. وضعیت `catalogueStatus` صرفاً حقیقت record کاتالوگ را نگه می‌دارد، اما وضعیت selection به `manufacturer-evidence-required` می‌رسد تا زمانی که evidence کامل و قابل‌ردیابی ثبت شود. این تغییر از تبدیل ابعاد یا نام مدل کاتالوگ به ادعای envelope یا performance map جلوگیری می‌کند.

APIهای read/validation بدون mutation به شرح زیر هستند:

```text
POST /api/core/manufacturer-evidence/validate
POST /api/core/pilot/golden-cases/validate
POST /api/core/pilot/readiness/evaluate
```

## 4. Golden cases و کنترل variance

`GoldenCaseRegistry` golden case را فقط برای R717 و R744 در scope فعلی می‌پذیرد. هر case شامل design basis، operating conditions در SI، source ledger، expected review decisions و امضای انسانی است. fixture regression تنها وقتی خروجی می‌دهد که status بازبینی `approved-for-regression` باشد؛ fixture هیچ مقدار load، ظرفیت، سایز لوله، مدل تجهیز یا نتیجهٔ محاسباتی جدید تولید نمی‌کند.

Taxonomy علت variance محدود و صریح است: input basis، thermophysical provider، calculation method، manufacturer map/envelope، P&ID graph/port mapping، BIM geometry/routing، reviewer decision و external project change. هر category خارج از این taxonomy `unresolved` تلقی می‌شود و G2 را مسدود می‌کند.

## 5. Scorecard و گیت‌های G0 تا G4

`PilotScorecard` صرفاً دادهٔ واردشده را اندازه‌گیری می‌کند. eventهای intake-complete، review-ready، review-decision، rework-started و rework-complete تنها با timestamp ISO-8601 و actor نام‌دار ثبت می‌شوند. completeness ratio فقط نسبت evidence records کامل در دادهٔ واردشده است؛ این ratio ادعای completeness کل پروژه نیست. defect بحرانی فقط با `escaped: true|false` صریح وارد می‌شود؛ مقدار پیش‌فرض وجود ندارد.

| gate | شرط اصلی مسدودکننده |
|---|---|
| G0 | health provider نامعتبر، golden case امضانشده یا source ledger ناقص |
| G1 | semantic graph ناقص یا cross-refrigerant contamination |
| G2 | variance بدون root cause، scorecard بدون measurement یا critical escape ثبت‌شده |
| G3 | نبود review pack revision یا approval record یا blocker در gateهای قبل |
| G4 | نبود scorecard اندازه‌گیری‌شده یا feedback record قابل‌ردیابی design partner |

حتی زمانی که تمام evidenceهای ورودی کامل باشند، G1 تا G4 در وضعیت `review-required` باقی می‌مانند و `finalIssueAllowed` همیشه `false` است.

## 7. وضعیت HVAC و Electrical

HVAC و Electrical در registry محصول همچنان **planned/blocked** هستند. این گزارش هیچ engine یا calculation capability جدیدی برای آن دو رشته ادعا نمی‌کند. ترتیب مجاز شروع HVAC فقط پس از عبور evidence gateهای تبرید و با contract مستقل است: intent/evidence schema، weather provider revisioned، psychrometric provider SI با provenance، سپس zone load، ventilation/air-side، hydronic/selection/controls و در انتها graph/delivery.

| رشته | وضعیت فعلی | شرط خروج از blocked |
|---|---|---|
| Refrigeration | governed-beta / pilot evidence path | golden case واقعی امضاشده، evidence سازنده و design-partner review |
| HVAC | planned/blocked | intent، weather، psychrometrics، test vectors و review gateهای مستقل |
| Electrical | planned/blocked | engine، source-backed data، safety/coordination evidence و review gateهای مستقل |

## 8. موارد باقی‌مانده پیش از پایلوت واقعی

برای آغاز G0 واقعی هنوز دادهٔ مهندسی واقعی و مالک آن لازم است: scope charter یک design partner، golden case ناشناس‌سازی‌شده با source ledger و امضا، performance map و envelope مجاز سازنده برای مدل‌های نامزد، evidence شرایط محیطی/اقلیمی revisioned، reviewerهای نام‌دار و record بازبینی. هیچ‌کدام از این داده‌ها در code یا test fixture جعل نشده‌اند.

همچنین اختلاف numeric مشاهده‌شده در parallel comparison legacy/CoolProp یک discrepancy review است، نه basis انتخاب. قبل از استفاده در هر design case باید method، reference state، applicability و manufacturer map توسط مهندس مسئول بررسی شود.

## 10. جمع‌بندی

مسیر نرم‌افزار اکنون برای واردکردن evidence واقعی و اجرای پایلوت کنترل‌شده آماده‌تر است، اما آمادهٔ صدور طراحی نهایی نیست. پیشرفت معتبر بعدی نه افزودن mock data، بلکه ورود golden case امضاشده، evidence سازنده مجاز و measurement واقعی از design partner خواهد بود.
