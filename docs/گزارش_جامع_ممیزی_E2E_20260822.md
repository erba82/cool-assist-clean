# گزارش جامع ممیزی E2E — Cool-Assist

**سناریوی ممیزی:** سردخانه صنعتی گوشت منجمد در دبی، امارات؛ بار نامی 500 کیلووات؛ مبرد R717؛ تبخیر `−30°C`؛ تقطیر `+35°C`؛ تغذیهٔ پمپ آمونیاک، دو کمپرسور اسکرو، کندانسور تبخیری، رسیور افقی، سپراتور مکش فشارپایین، ترموسیفون و شاخهٔ IQF با Danfoss ICF 25-4 / DN32.
**تاریخ اجرا:** 22 اوت 2026، ساعت محلی کاربر.
**وضعیت سند:** گزارش فنی و ممیزی؛ **نه** تأییدیهٔ ساخت، انتخاب نهایی تجهیز، خرید یا انطباق قانونی.

> **نتیجهٔ اجرایی:** سناریوی browser-based از ابتدا تا انتها اجرا شد. هر 11 check اصلی شامل طراحی، دفترچه، BOM، تجهیزات، P&ID دوبعدی، BIM سه‌بعدی، انرژی، compliance و گفت‌وگوی عمومی موفق بودند. افزون بر آن، نقص مسدودشدن پنجرهٔ «Create New Project» بازتولید و اصلاح شد و تست پایداری مستقل آن چهار check را با موفقیت گذراند. با وجود این موفقیت اجرایی، خروجی هنوز برای issue-for-construction، خرید یا compliance approval آماده نیست؛ علت‌های اصلی، evidence ناکافی سازنده، تفاوت بزرگ legacy/sidecar در R717، BOM بدون quotation منبع‌دار و نیاز به بازبینی مهندسی مستقل هستند.[1] [2] [3]

## 1. دامنه و روش ممیزی

آزمون با Playwright و browser محلی، روی frontend فعال و backend/sidecar در حال اجرا انجام شد. پس از ارسال درخواست طراحی، موتور طراحی وارد مسیر reviewable proposal شد، سپس همهٔ tabهای موجود باز شدند. Tierهای مالی به‌ترتیب `Tier 1 → Tier 2 → Tier 3 → Tier 1` تغییر داده شدند. در بخش AI نیز پاسخ عمومی جدا از مسیر طراحی با router حاکمیتی آزمون شد. در پایان، build تولیدی frontend، regression حاکمیتی backend و regression اختصاصی CoolProp اجرا شدند.[1] [4] [5]

| آزمون | نتیجه | تفسیر معتبر |
|---|---:|---|
| E2E طراحی R717 دبی | **11/11 موفق** | UI، ارتباط مسیرها و render tabها برقرار است؛ این عدد اثبات صحت نهایی مهندسی نیست. |
| ایجاد پروژه و پایداری Dialog | **4/4 موفق پس از اصلاح** | Dialog باز شد، پس از Create بسته شد، پس از navigation دوباره باز نشد و مسیر پروژه صحیح بود. |
| Build تولیدی frontend | **موفق** | فقط دو هشدار اندازهٔ bundle باقی است: `vendors` حدود 2.4 MiB و `three` حدود 777 KiB. |
| `npm test` در backend | **موفق** | gateهای چندمبردی، evidence، learner، sidecar، elevation hint، MCP/attachment و orchestrator گذشتند. |
| `npm run test:coolprop-sidecar` | **موفق** | sidecar loopback-only، هشت fluid mapping و fail-closed gateها کنترل شدند. |

## 3. ارزیابی موتورها و قابلیت‌ها

### 3.1 موتور طراحی و P&ID/BIM

برای R717، profile semantic، template چرخهٔ `pumped_ammonia_industrial` و policy لوله‌کشی جوشی در مسیر طراحی برقرار است. P&ID دارای 21 تجهیز، 21 outlet اعلام‌شده و 21 line بود؛ scene سه‌بعدی نیز 21 process line و 21 rack/support element را نشان داد. این موضوع نشان می‌دهد ارتباط 2D→3D از سطح demo خالی عبور کرده است. با این حال، سیستم خود UI، connect handleها و خروجی را review-required معرفی می‌کند؛ بنابراین از روی render نباید پیوستگی فیزیکی هر nozzle، class فشار، سایز واقعی، weld procedure، support load یا accessibility را تأیید کرد.[1]

قواعد ارتفاعی مهم در testهای backend پوشش یافته‌اند: pump پایین‌تر از LP separator، LP separator بالاتر از compressor preview و thermosiphon/oil-cooler به‌صورت head جداگانه. این کنترل‌ها guardrail ارزشمندی هستند، اما هنوز جایگزین مدل elevation با datum، profile واقعی سازه، clearance تعمیراتی و بازبینی مسئول طراحی نیستند.[4]

### 3.2 محاسبات و خواص ترموفیزیکی

CoolProp sidecar نسخهٔ 8.0.0 با backend `HEOS`، reference state `IIR`، binding loopback و mapping هر هشت مبرد سالم است. درخواست property-dependent در نبود یا stale شدن provider fail-closed می‌شود و R744 نیز برای booster/transcritical به controlهای صریح نیاز دارد؛ این رفتار از ساخت عدد جایگزین جلوگیری می‌کند.[5]

با وجود آن، مقایسهٔ موازی R717 با legacy تفاوت معنادار نشان داد: COP حدود `−74.3707%`، توان کمپرسور `+290.2025%` و heat rejection `+31.2365%` در نتایج مقایسه ثبت شده‌اند؛ تنها فشارهای تبخیر/تقطیر نزدیک‌اند. در نتیجه، legacy calculation به هیچ‌وجه نباید مبنای نهایی sizing یا خرید باشد. گام درست، تصویب vectorهای مستقل توسط مهندس واجد صلاحیت، ثبت envelope و reference state و سپس محدود کردن/بازنشسته‌کردن مسیر legacy در حوزه‌های اختلاف است.[5]

### 3.3 انتخاب تجهیزات و کتابخانهٔ سازنده

هشت مبرد در سطح semantic پشتیبانی می‌شوند: R717، R744، R290، R32، R404A، R410A، R134a و R22. cycleهای R717 و R744 اختصاصی‌اند و profileهای دیگر DX-based هستند. با این حال، regression، compressor selection را برای profileهای آزمون‌شده `unmapped` گزارش کرد. همچنین catalogue readiness دارای category منبع‌دار فقط برای R717 و R22 است و برای R744، R290، R32، R404A، R410A و R134a مقدار صفر گزارش شده است. بنابراین عبارت «پشتیبانی هشت مبرد» در این نسخه به معنی **profile/cycle/P&ID/BIM semantic support** است، نه انتخاب قطعی تجهیز قابل خرید برای همهٔ آن‌ها.[4]

### 3.4 Procurement و BOM

تغییر tier با E2E انجام شد و UI موقعیت Dubai/AE و currency هدف AED را نشان می‌دهد. در عین حال، نمونهٔ visible کمپرسور دارای `No sourced offer`، مبلغ `—`، availability `not-found` و regional reference `Quote required` بود. بنابراین $332,016 نمایش‌داده‌شده در summary یک estimate کاربردی برای سناریوسازی است، نه quote قابل استناد، landed cost یا پیشنهاد خرید. پیش از استفاده در procurement باید supplier، مدل، revision، Incoterms، حمل، گمرک، FX timestamp و validity quotation ضمیمه شود.[1]

### 3.5 Energy و Compliance

Energy Hub به‌درستی baseline/meter coverage را input-required و electrical connected load را review-required نگه می‌دارد. در نتیجه، صرفه‌جویی مالی یا انرژی بدون baseline و M&V جعل نشده است. Compliance نیز ASHRAE 15/34، ASME BPVC VIII/B31.5 و IIAR را review-required نگه می‌دارد و automation را approval تلقی نمی‌کند. این دو کنترل از مهم‌ترین نقاط قوت حاکمیتی محصول‌اند.[1]

### 3.6 AI router و یادگیری کنترل‌شده

ترتیب حاکمیتی router به‌ترتیب NVIDIA، Gemini، Qwen، DeepSeek محلی و DeepSeek remote است؛ precedence provider ثابت می‌ماند و adaptive ranking فقط profileهای واجد شرایط درون یک provider را تغییر می‌دهد. Snapshot پایانی 30 روزه نشان داد NVIDIA Super دارای 6 attempt، 5 success، نرخ `83.33%` و latency میانگین `24,742 ms` است. Gemini Flash یک attempt موفق با `27,753 ms` دارد و NVIDIA Ultra یک attempt ناموفق با `1,581 ms` ثبت کرده است. این sample برای تصمیم‌گیری عملکردی قطعی کوچک است، اما provenance و telemetry را قابل مشاهده می‌کند.[6]

یادگیری خودکار به MongoDB متصل است، اما تغییر خودکار engineering rule، نصب خودکار skill و promotion به production مسدود است. این دقیقاً با اصل «از تعامل یاد بگیر، اما rule/selection/safety را بدون تأیید انسان تغییر نده» سازگار است.[7]

## 6. اصلاحات انجام‌شده در همین مرحله

نقص باقی‌ماندن modal پس از ایجاد پروژه بازتولید شد. اصلاح، بسته‌شدن dialog را پیش از route change commit می‌کند و یک guard برای جلوگیری از بازشدن مجدد ناشی از event portal افزوده است. Playwright اکنون بازشدن dialog، بسته‌شدن پس از Create، بسته‌ماندن پس از navigation و مسیر `/chat/proj_*` را پاس می‌کند.[2]

در chat design-mode، اتصال رشته‌ای فیلدهای optional با join type-safe جایگزین شد؛ بنابراین `undefined` در پاسخ `question_response` یا `unknown` نمایش داده نمی‌شود. برای general chat فارسی نیز prompt حاکمیتی زبان و مفهوم direct/indirect تقویت شد. پاسخ نهایی از نظر script contamination بهتر شد، اما حضور برخی واژه‌های عمومی انگلیسی نشان می‌دهد این اصلاح، **بهبود کنترل‌شده** است نه localization نهایی.[8] [1]

## 7. جمع‌بندی آمادگی پایلوت

| محور | وضعیت فعلی | حکم ممیزی |
|---|---|---|
| R717 demo / reviewable proposal | عملیاتی با gate | برای demo و review مهندسی محدود مناسب است. |
| R717 construction/procurement issue | مسدود | تا evidence سازنده، performance map، PHA/compliance و independent review تکمیل نشود مجاز نیست. |
